# Multi-Harness Selection — Design Spec

**Date:** 2026-07-29
**Status:** DESIGN — revised after Opus review (rounds 1-3); pending round 4
**No existing deployments to preserve.** There are no users on this schema yet — `schema.json`/migration files are modified directly, with no additive-only or backward-compatibility constraint. This removes an entire category of risk the first two revisions were hedging against; see §9.
**Grounded against (code, not docs):** `server/pocketbase/internal/agent/coordinator/{run.go,profile.go,admin.go,delete_session.go}`, `server/pocketbase/internal/api/{profile.go,agent.go,skills.go,schedules.go}`, `server/pocketbase/internal/hooks/{goose_config.go,mcp_gateway.go,schedule_importer.go,cognee_extension.go,timestamps.go,docker.go}`, `server/pocketbase/pb_migrations/{schema.json,1756000000_schema.go,1756000100_seed.go}`, `docker-compose.yml` (goose + docker-socket-proxy-write services), `client/packages/pocketcoder_flutter/lib/{presentation/chat/chat_list_screen.dart,application/chat/chat_list_cubit.dart,infrastructure/chat/chat_list_repository.dart,domain/chat/i_chat_list_repository.dart}`, PocketBase `core/field_relation.go`/`core/field_json.go`/`core/record_model.go` (v0.36.1, per `go.mod:10`).

## 1. Why this exists

The user wants to be able to run different agent harnesses — not just different models within one harness, but genuinely different harness binaries (goose fronting a provider today; a bare stdio ACP agent like `claude-agent-acp` with no goose in front, as the concrete next one) — and pick cwd + harness + model explicitly per chat, the same way a terminal user picks a working directory and a CLI before starting a session. Nothing in the codebase currently supports more than one harness *type*; the goal is to make that real, without over-building automatic isolation machinery the user explicitly does not want yet.

## 2. Current state, verified directly from code (not from prior specs)

- **`docker-compose.yml`**: exactly one `goose` service. `Coordinator.New()` (`run.go:110-113`) hard-requires a single `GooseURL`/`GooseSecret`/`Workspace`. The default `DialFunc` closure built in `New` (`run.go:114-118`) captures these at construction — but `Dial` itself is an injectable field on `Config` (already used by tests), not a hardcoded call, which matters for §5.1's fix.
- **Per-chat model/provider switching within goose already works.** `initSession` (`run.go:772-822`) calls `applier.Apply(...)` on every session. `selectApplier` (`profile.go:145-147`) **unconditionally** returns `PerSessionApplier`, ignoring the `*acpsdk.InitializeResponse` argument it's given — today that's harmless because there is only ever one harness (Goose) to select for. `PerSessionApplier.Apply` (`profile.go:103-137`) issues standard ACP `session/set_config_option` for `provider`/`model`, confirmed against goose v1.43.0, **plus** a Goose-private custom method `_goose/unstable/session/system-prompt/set` (`profile.go:130`) for instructions. `buildSessionProfile` (`api/profile.go:43-118`) resolves `chats.harness_model_override` (falling back to `poco_config.harness_model`) into this live path. **The live-switching mechanism itself needs no new design work — but `selectApplier`'s unconditional choice becomes a live bug the moment a second, non-Goose harness exists** (see §6.4).
- **`buildSessionProfile` has an early-return bug that matters a lot for this design.** `api/profile.go:61-66`: when `poco == nil` (no `chats.poco_config` set *and* no `is_default` `poco_config` exists — the actual state of a fresh deployment, since `1756000100_seed.go` seeds none of `harnesses`/`models`/`harness_models`/`poco_configs`/`provider_keys`), the function returns immediately, **before** reading `harness_model_override` (line 70) or `workspace_folders` (lines 93-99). So on a fresh box, chat-level overrides are silently ignored. This must be fixed as part of this work, not treated as pre-existing and out of scope, because harness resolution (§5.1) depends on exactly the fields this bug skips.
- **No per-chat cwd.** `profile.Cwd` comes only from `poco_configs.workspace_folders`, shared by every chat using that `poco_config`. `docker-compose.yml` mounts one `goose_workspace` volume into both `pocketbase` and `goose`, declared with no `name:`/`external: true` — the real Docker object is `<compose-project>_goose_workspace`, not a name known in advance (see §5.1.2).
- **`harnesses` is a static, currently-empty catalog** (`pc_harnesses`: `name`, `cli_id` unique, `version`, `description`, `acp_transport` ∈ `{websocket, stdio, http}`). No seed rows exist. It describes harness *types* but has no field describing how to actually run one, and nothing in the code provisions a container from it.
- **`docker-socket-proxy-write`** (`docker-compose.yml:203-227`) grants `CONTAINERS=1`, `POST=1`, `EVENTS=1`, and explicitly `IMAGES=0`/`NETWORKS=0`/`VOLUMES=0`. `CONTAINERS`+`POST` is enough for container create/start/stop. `EVENTS=1` allows subscribing to the Docker event stream. `IMAGES=0` means **PocketBase cannot pull an image it doesn't already have locally** — creating a container from a missing image fails outright, with no fallback (§5.1.1, this is a real gap in the original draft of this spec). (An earlier revision also noted `EXEC=0`/attach as relevant to stdio harnesses; superseded by §5.4's bundled-adapter decision, which needs neither.)
- **`AdminConn`** (`admin.go:76-88`) dials the single configured Goose with no chat/harness context at all, and is itself a **fourth dial site** alongside `run.go:547`/`run.go:726`/`delete_session.go:54` (round 1 undercounted this as covered by "two call sites"). Its 8 callers: `hooks/goose_config.go:232`, `hooks/mcp_gateway.go:85`, `hooks/schedule_importer.go:136`, `hooks/cognee_extension.go:85`, `api/skills.go:286,306`, `api/schedules.go:168,462` — several use Goose-private custom methods. §5.5 pins `AdminConn` to the default Goose deliberately, which is what makes it *not* need the new `Target` parameter (see §6.2) — not an oversight.
- **`goose_sessions` has `UNIQUE(chat)` and `UNIQUE(goose_session_id)`.** A chat maps to exactly one session id, globally, minted by whichever agent process created it and only loadable there. `schedule_importer.go:96-102` is a **second write site** for this collection (imported chats, inside a transaction), separate from `initSession`'s `saveGooseSession` (`api/agent.go:389-402`) — both need to agree on what they stamp for harness identity (§5.6).
- **No client-facing selection UI.** `ChatListCubit.createAndOpen()` → `ChatDao.save({title, user})` only — no `poco_config`, `harness_model_override`, or workspace field is ever set from the client, even though the `Chat` model already carries `pocoConfig`/`harnessModelOverride` fields unused by the create path.

## 3. Goal and explicit non-goals

**Goal:** a user creating a new chat picks cwd + harness + model, and the system runs whichever harness container that implies, routing that chat's ACP session to it.

**Explicit non-goals (YAGNI, confirmed):**
- No automatic per-chat worktree or workspace isolation. cwd is the user's own explicit choice, same as `cd`-ing before running a terminal CLI. If two chats collide on one directory, that's the user's call, not a system guarantee. (A later PocketBase-side "create a worktree for me" convenience is plausible future work, explicitly deferred.)
- No live agent-to-agent protocol between harnesses. If harnesses need to share output, that's the shared workspace volume, nothing more.
- No arbitrary bring-your-own Docker image reference from an end user. A harness is provisioned from a catalog entry (`harnesses` row), which only a superuser can create (`createRule: null` today, unchanged) — so "extensibility" means "an admin adds a catalog row," not "any user supplies an image string." Given every deployment is the user's own VPS, not shared infra, this is a much lower-stakes trust boundary than a multi-tenant SaaS, which is why §5.1.1 is comfortable proposing `IMAGES=1`.
- **No longer a non-goal: stdio-transport harnesses.** The original draft excluded these, which contradicted §1's own motivating example (`claude-agent-acp` is stdio). §5.4 covers this properly instead of carving it out.

## 4. Schema changes

### 4.1 `chats` — add `workspace_override` and `harness`

- **`workspace_override`** (json, nullable — PocketBase's JSON columns are genuine `NULL`-capable, unlike relations, so "unset" and "explicitly empty" are distinguishable). Same element shape as `poco_configs.workspace_folders`, but see §5.7 for exactly how it composes with the poco's value — it does **not** simply replace the whole array.
- **`harness`** (relation → `harnesses`, `maxSelect: 1`, not required). Needed because harness selection cannot only be derived from model choice (§5.6.1) — a harness with no `harness_models` rows (e.g. one with its own baked-in subscription auth and no PocketCoder-visible model list) would otherwise be unselectable.
- New non-unique index `CREATE INDEX idx_chats_user_archived ON chats (user, archived)` — `chats` has zero indexes today, and this design is adding lookups on the collection anyway (client-side harness/model filtering), so an additive index is cheap to include now.

### 4.2 `harnesses` — add provisioning fields, and split the overloaded capability flag

- `container_image` (text, **not required** — round 3 found the compose-managed default Goose row (§5.2) has no real image/launch_template of its own, since PocketBase never creates that container, and `required: true` forced it to carry fake values) — the image PocketBase creates a container from. Required only in practice for `managed = true` instances (enforced by the provisioning code path, not the schema, mirroring how `harness_instances.managed` already isn't schema-enforced against these fields).
- `launch_template` (json, not required — same reasoning as `container_image` above) — command/env shape PocketBase renders when creating an instance. Must express: entrypoint `cmd`, `env_template` (may reference `{{provider_key_env}}`-style placeholders resolved from `provider_keys` at create time — see §5.5 for why this is create-time, not live, for non-Goose harnesses), and the ACP port the bundled adapter (§5.4) listens on — every harness is websocket at the boundary (§5.4), so there is no transport branch to express here at all; `acp_transport` (§2) stays purely descriptive of what the underlying binary natively speaks.
- `supports_live_config` (bool, default `true`) — whether this harness type can switch provider/model per session at runtime without restarting (Goose: `true`, confirmed). Drives whether an instance is shared across models (`true`) or pinned to one model at launch (`false`) — see §4.3.
- **`supports_goose_extensions`** (bool, default `false`, **new — separates a concern the original draft conflated with `supports_live_config`**) — whether this harness understands Goose's private custom ACP methods (`_goose/unstable/...`). Goose itself: `true`. A bare `claude-agent-acp` process: `false`, even though it may independently support the *standard* ACP `session/set_config_option` (i.e. `supports_live_config` and `supports_goose_extensions` are orthogonal, not the same bit — see §6.4).

### 4.3 New collection `harness_instances` — runtime container tracking

Tracks containers PocketBase has actually provisioned (or, for the compose-managed default Goose, is aware of), distinct from the static `harnesses` catalog. A row exists once any chat has selected that harness (or harness+model combo), whether or not the container is currently up.

| Field | Type | Notes |
|---|---|---|
| `id` | text (PB-owned PK) | |
| `harness` | relation → `harnesses`, required | |
| `harness_model` | relation → `harness_models`, not required | denormalized convenience for `expand` only — **not** the uniqueness key, see below |
| `launch_key` | text, required | `""` for a `supports_live_config = true` harness (one instance serves every model); otherwise the `harness_models.id` this instance was launched with. This, not `harness_model`, is what uniqueness is keyed on — see rationale below |
| `container_name` | text, required | the actual Docker container name |
| `acp_endpoint` | text, not required | e.g. `ws://<container_name>:3000/acp`; **empty means "use `Coordinator.Config` defaults"** — this is how the compose-managed Goose is represented (§5.6.3), not as a special case in code |
| `secret` | text, not required | **new — round 3 found `Target{URL, Secret}` (§6.1) had no field to populate `Secret` from.** Minted by PocketBase at create time for a `managed = true` instance (the bundled adapter, §5.4, is told the same value via `launch_template.env_template` so it can enforce `?token=` per §5.4.1); empty for the compose-managed Goose row, which uses `Coordinator.Config.GooseSecret` (`GOOSE_SERVER__SECRET_KEY`) instead — the same "empty means use `Config` defaults" convention as `acp_endpoint` |
| `status` | select: `pending`\|`running`\|`stopped`\|`error` | updated by the event watcher (§5.3) |
| `last_error` | text | e.g. `"No such image"` — surfaces §5.1.1 failures to an admin instead of a silent stuck `pending`/`error` row |
| `managed` | bool, default `false` | `true` = PocketBase created this container and may stop/remove it; `false` = compose-managed (the default Goose) and must never be touched by the provisioning/reconciliation code |
| `created` / `updated` | autodate | not present on `harnesses` today; added here because instance lifecycle (and future idle-stop work, §7) needs timestamps |

Indexes:
```
CREATE UNIQUE INDEX idx_harness_instances_name ON harness_instances (container_name)
CREATE UNIQUE INDEX idx_harness_instances_pair ON harness_instances (harness, launch_key)
```

**Why `launch_key` (a required text sentinel) instead of a nullable `harness_model` relation for the uniqueness key** — corrects a factual error in the original draft. PocketBase does **not** store an unset single relation as SQL `NULL`: `RelationField.ColumnType` (`core/field_relation.go`) is `"TEXT DEFAULT '' NOT NULL"` for a non-multiple relation, so an unset `harness_model` is the empty string `''`, which compares equal to `''` under a unique index exactly as you'd want — a naive `UNIQUE(harness, harness_model)` would in fact have worked, no app-level race needed. `launch_key` is used anyway, not `harness_model` itself, because it's self-documenting (the column name states what it means: "the part of the config frozen into the container at create time") and it's the natural place to extend to a third pinning axis later (e.g. a sandbox profile) without another schema decision — `launch_key` would just become a hash of the frozen launch config, no index change required. `harness_model` stays purely for `expand` convenience in the API/UI.

API rules for this new collection (the original draft omitted these — a new collection with unset rules is invisible to the client, which breaks §6): `listRule`/`viewRule`: `"@request.auth.id != ''"` (matches `harnesses`); `createRule`/`updateRule`/`deleteRule`: `null` (superuser/backend-only — PocketBase's own provisioning code writes these, not end users).

## 5. Runtime behavior

### 5.1 Chat → instance resolution

`buildSessionProfile` resolves, in order: `chat.harness` if set, else `harness_models.harness` of the resolved model (`chat.harness_model_override` or the poco's `harness_model`), else the implicit default (today's single Goose). It then looks up the matching `harness_instances` row (keyed on `(harness, launch_key)` — `launch_key` is `""` unless the harness has `supports_live_config = false`, in which case it's the resolved `harness_models.id`). If no row exists, provision one (§5.1.1/§5.1.2) before dialing.

#### 5.1.1 Getting the image onto the box

`docker-socket-proxy-write` currently has `IMAGES=0`. `POST /containers/create` fails with "No such image" if the image isn't already local, and there is no pull path with `IMAGES=0`. This spec picks: **flip `IMAGES=1` on `docker-socket-proxy-write`.** This is a real proxy config change (the original draft incorrectly claimed none was needed) but a defensible one: `harnesses.container_image` is only ever superuser-written (§3), so the proxy would only ever be asked to pull images an admin already put in the catalog, not arbitrary end-user strings — consistent with the single-user-VPS trust model this whole spec leans on elsewhere. `harness_instances.last_error` (§4.3) surfaces a failed pull/create instead of it disappearing into a stuck `pending` row. One side effect worth naming rather than discovering later: `IMAGES=1` combined with the existing `POST=1` also opens image delete/prune through the proxy, not only pull — low-severity here, since `CONTAINERS=1`+`POST=1` already permits deleting any container, so this doesn't cross a trust boundary that wasn't already open.

#### 5.1.2 Resolving the real volume/network names

`goose_workspace` and `pocketcoder-agent` are declared without `name:`/`external: true`, so the real Docker object names are compose-project-prefixed and not knowable at compile time — and they will differ between a dev checkout and an Aeroform-provisioned box. Passing a wrong **volume** name to `POST /containers/create` does not error — Docker silently creates a new, empty volume, and the harness comes up "successfully" pointed at an empty `/workspace`. A wrong **network** name does at least error.

Fix: at PocketBase startup, `GET /containers/pocketcoder-pocketbase/json` (allowed under `CONTAINERS=1`). `pocketcoder-pocketbase` has multiple mounts and joins multiple networks (`docker-compose.yml`), so this cannot be "read *the* volume/network name" — it must be a specific match: the volume is the one whose `Mounts[].Destination == "/workspace"`; the network is the one among `NetworkSettings.Networks` whose name has suffix `pocketcoder-agent` (the only network both `pocketbase` and `goose` join). Cache both for use in every subsequent `harness_instances` create. Given there are no existing deployments to preserve (see header), the simpler fix is to just pin explicit `name:` values for both objects directly in `docker-compose.yml` now — the runtime lookup above is a reasonable belt-and-suspenders fallback but pinning removes the ambiguity at the source.

`NETWORKS=0` also blocks `POST /networks/{id}/connect` — meaning the network **must** be attached via `NetworkingConfig` in the container-create call itself, not as a follow-up call. `launch_template` rendering must account for this.

### 5.2 What a fresh box looks like, and the default-Goose row

The implicit default (no `chat.harness` and no resolvable `harness_models.harness`) still means "today's compose-managed Goose," represented as a **seeded** `harness_instances` row: `harness` → the seeded `goose` catalog row, `managed = false`, `container_name = "pocketcoder-goose"`, `acp_endpoint = ""` (meaning: use `Coordinator.Config`'s existing `GooseURL`/`GooseSecret`, not a resolved instance URL). This removes the special-case branch that "the default case still resolves to today's single Goose instance" would otherwise require in code — resolution always ends at a `harness_instances` row, full stop; that row's `managed = false` is what tells the reconciliation/teardown code in §5.3 never to touch it.

### 5.3 Reactive status tracking

A watcher subscribes to the Docker event stream via `EVENTS=1` and updates the matching `harness_instances.status` on container start/die/health-change — **but subscribe first, then sweep**: on PocketBase startup, subscribe to `/events` before running a one-time `GET /containers/json?all=1` reconciliation pass, so a container that died while PocketBase was down (which would otherwise leave its row stuck at `running` forever, since no event was ever consumed for it) gets corrected without a gap where an event fires between the sweep and the subscription. The sweep, and any stop/remove the watcher ever issues, must skip every row with `managed = false`.

### 5.4 stdio-native harnesses get a bundled ws adapter — every harness_instance is websocket at the boundary

`claude-agent-acp`/`codex-acp` — the concrete harnesses §1 is motivated by — are stdio-only: verified against both projects' docs/source and the ACP spec itself (`agentclientprotocol.com/protocol/transports`), which formally defines only **stdio** (stable) and a still-**draft** Streamable HTTP transport — no websocket at all. Goose's `goose serve --host 0.0.0.0` websocket server is Goose's own extension beyond the spec, not a standard ACP transport other agents can be expected to share. An earlier revision of this spec considered having the coordinator attach directly to a stdio harness's container (`POST /containers/{id}/attach`) and multiplex concurrent chats over one process's single stdin — rejected: ACP's per-session multiplexing works over one *connection*, but ties one process to one stdin, so two concurrent chats attached to the same container would interleave JSON-RPC frames on one pipe. That's a real protocol/OS mismatch, not just extra code.

**Decision: every harness, stdio-native or not, exposes `websocket` at `harness_instances.acp_endpoint`.** For a stdio-native binary, its `container_image`/`launch_template` bundles a small adapter process (built and owned by this project, since no upstream one exists) that listens on the harness's ACP port and, per incoming websocket connection, spawns the underlying binary fresh as a stdio subprocess and relays JSON-RPC frames both directions. This makes `harness_instances` and the coordinator's dial path **transport-uniform** — no attach-stream variant, no connection pooling, no `Dial` branching by transport at all; §6.1's `Target{URL, Secret}` is exactly what already works for Goose today, for every harness.

Spawn-per-connection is correct only if the underlying binary can resume a given session id's history from its own on-disk persistence when started fresh (the Claude Agent SDK's `--resume`-style session persistence is expected to support this) — call out per-harness whether this holds as part of adding that harness's catalog row; it is not something this schema encodes or guarantees generically. `harnesses.acp_transport` stays as a descriptive field (what the underlying binary natively speaks) but no longer determines how the coordinator dials — that's uniformly `Target{URL, Secret}` regardless.

#### 5.4.1 The bridge's wire shape is standardized against the existing Goose adapter, not invented fresh

`internal/agent/acp/websocket.go` (`wsStream`/`Dial`) is the coordinator's *client*-side implementation of exactly this shape already, proven against Goose's `goose serve` server side. The new in-container adapter is that shape's **server** side, for a stdio subprocess instead of Goose's native WS server — same framing, so the coordinator's existing client code is reused unmodified for every harness, not forked per transport:

- **Framing: exactly one JSON-RPC message per WebSocket TEXT frame, both directions.** `wsStream.Write` (`websocket.go:90-109`) buffers arbitrary byte writes and flushes only on each `\n`-terminated line as one `websocket.MessageText` frame; `wsStream.Read` (`websocket.go:78-88`) does the reverse, appending `\n` to each received frame before handing it to the newline-delimited JSON-RPC reader `acpsdk.NewClientSideConnection` expects. The adapter's server side must produce/consume the identical framing: one subprocess stdout line in → one TEXT frame out; one TEXT frame in → one stdin line out (plus its trailing `\n`) to the subprocess. This is ACP's own stdio wire format (newline-delimited JSON-RPC) carried unchanged across the socket — the adapter reframes, it does not reinterpret.
- **No data loss requires two explicit size limits raised, not one.** The existing client sets `conn.SetReadLimit(64 << 20)` (`websocket.go:131`) precisely because the `coder/websocket` library's default frame-size limit (32 KiB) would silently truncate or error on a large message (a big diff, an embedded file, a long tool result) — the adapter's WS server side must set the equivalent generous limit on its end of the socket. **The line the first two spec revisions didn't flag**: the *stdio* leg has its own default limit that would truncate first if unaddressed — a naive `bufio.Scanner`-based line reader over the subprocess's stdout defaults to a 64 KiB token size in Go's standard library, well below the 64 MiB the WS leg already tolerates. The adapter must explicitly raise (or avoid entirely, via an unbounded `bufio.Reader.ReadString('\n')`) the stdio-side line limit to match — otherwise "full capabilities, no dropped data" fails silently at exactly the boundary this design is meant to erase, and it would fail differently (and more confusingly) than the well-understood WS-side limit this codebase already had to learn once.
- **Auth, matching and hardening the existing pattern**: `?token=<secret>` query param on the WS upgrade URL (`wsURLWithToken`, `websocket.go:39-51`) — required because browser-origin WebSocket clients can't set arbitrary headers, though nothing here is browser-facing; kept for consistency, not because it's load-bearing in this direction. Unlike the existing client's documented gap (`websocket.go:141-142`: Goose v1.36.0 historically didn't enforce this on its own WS endpoint — fixed upstream in v1.39.0), the **new adapter is a server we write**, so it must enforce the token at the WS upgrade from day one, not carry the same historical TODO forward.
- **Byte-transparency is what guarantees "no capability dropped in translation," not a design goal separately pursued**: because the adapter only reframes newline-delimited JSON onto WS frames and back — never parses, filters, or maps individual ACP method/notification shapes — every ACP surface a given stdio harness supports (session updates, tool-call args/results, elicitation, permission requests, whatever that specific binary implements) passes through unchanged. There is no ACP↔ACP semantic translation happening here at all, unlike the separate ACP↔AG-UI bridge in c1 (`docs/architecture-refactor.md`'s "frozen event contract") — this bridge's only job is transport, and it must stay that way; any temptation to have the adapter special-case or filter a message type would reintroduce exactly the data-loss risk this section exists to rule out.

### 5.5 What stays Goose-only in v1

`AdminConn` (tool-permission live delivery, MCP gateway attachment, schedule import, Cognee extension wiring, skills, schedules — 8 callers, §2) stays pinned to the compose-managed Goose instance. Non-Goose harnesses do not get any of this in v1 — explicitly documented here so it isn't discovered as a surprise gap during implementation. A consequence worth stating plainly: because a non-Goose harness's provider keys are baked into its `launch_template.env_template` at container-**create** time (there is no per-session or config-render-and-restart path for it, unlike Goose's `keys.env`), **rotating a provider key for a non-Goose harness means destroying and recreating its container**, not a restart. This is a real regression relative to Goose's rotation story and is accepted for v1, not solved.

### 5.6 Session establishment is unified into one path — this is what fixes pinning, capability checks, and the concurrent-connection hazard together

Round 2 added a write-time `chats` hook to block harness re-homing after a session exists; round 3 found it insufficient (a TOCTOU window, and a bypass via reassigning `poco_configs.harness_model` — a write path the `chats`-scoped hook can't see at all) and, separately, that the proposed fix's stated location ("in `initSession`, before dialing") doesn't exist in the code: `initSession` (`run.go:772`) is only ever called *after* `c.config.Dial` (`run.go:726`), and `StreamColdReplay` (`run.go:521-566`) duplicates its own separate dial+init sequence rather than sharing `initSession` at all — so a fix aimed only at `initSession` silently misses half the dial sites.

**That duplication is itself pre-existing tech debt, independent of this feature, and this is the point to remove it.** `runLoop`'s job (start a new prompt, run it to completion) and `StreamColdReplay`'s job (replay durable history for a reconnecting subscriber when the in-memory `ChatHub` buffer can't cover it, per `hub.go`'s `ColdReplayNeeded`) are genuinely different — that distinction is real and stays. But the *shared* piece both currently duplicate — resolve target, dial, initialize, `session/new`|`load`, apply post-create config — should be exactly one function, not two independently-maintained copies. Introduce `establishSession(ctx, chatID, profile SessionProfile, sessionID string) (conn acp.Conn, newSessionID string, err error)` in `run.go`, called by both `runLoop` and by `StreamColdReplay`'s replacement (renamed away from "cold" — the hot/cold distinction that name encodes lives in `ChatHub`/`Attach`, one layer up, and stays there; this function's name should describe what it does: e.g. `replaySessionHistory`). This is not merely a naming exercise — it's what gives every fix below exactly one place to live, instead of two to keep in sync.

**Why PocketCoder never owning the conversation makes this the right shape, not just a convenient one:** the harness (Goose or otherwise) is the sole system of record for session history — `ChatHub`'s in-memory buffer is purely a RAM cache for cheap reconnects, never authoritative (confirmed by `docker-compose.yml`'s own comment on the goose service to this effect). So both callers' real job, underneath their different outer purposes, is identical: "get me a live, correctly-identified connection to this chat's actual session." One function doing that is the correct model of the system, not just less code.

`establishSession` is where every one of round 3's findings lands:

1. **Harness pinning, checked before dialing, for real this time.** Before resolving `Target` and dialing, compare it against `goose_sessions.harness_instance` (added below) if a row already exists for the chat. A mismatch is a hard, clearly-surfaced error ("this chat's harness changed after its session was created — start a new chat"), never a silent dial against the wrong harness. This is correct regardless of *how* the mismatch arose (a direct `chats.harness` edit, a reassigned `poco_config`, an edited `poco_configs.harness_model`, or a race) because the check no longer depends on catching a particular write path — every caller of `establishSession` goes through it. The remaining true TOCTOU (a harness change landing in the gap between this check and `saveGooseSession` actually persisting `goose_sessions.harness_instance` for a brand-new session) is closed by the *existing* `UNIQUE(chat)` index, not by this check: two racing `establishSession` calls for a new session both attempt `NewSession` + `saveGooseSession`, the second `saveGooseSession` fails the unique constraint, and `run.go:797-803`'s existing orphan-compensation path already deletes the loser's stranded remote session. State this explicitly rather than implying the pre-dial check alone closes every race — it closes the *reuse* case; the DB constraint closes the *creation* race.
2. **One connection per chat's session, enforced via the existing `Reserve`/`running` map, not a new lock.** Round 3's most serious new finding: `runLoop` and `replaySessionHistory` can dial concurrently for the same chat (a subscriber reconnecting with a stale cursor while a run is live), and under §5.4's spawn-per-connection stdio adapter that means two independent OS processes concurrently touching the same on-disk session file — a real hazard, not present when every harness was Goose serializing internally. Fix: `establishSession` checks `c.isReserved(chatID)` (already exists, `run.go:222-227`) before dialing for the *replay* caller specifically — if a run is already active for this chat, `replaySessionHistory` skips dialing entirely and serves only the hub's existing snapshot/buffered data (the live run's own `bridge.SeedSession`/`SessionUpdate` publishes already cover what a fresh `LoadSession` would have replayed). `runLoop` itself is already exclusive per chat via `Reserve` (`run.go:147-155`, `ErrRunInProgress`) and needs no new gating. Net effect: at most one dialed connection per chat's session, ever, for every harness — not just the ones where it happens to matter.
3. **`AgentCapabilities.LoadSession` is checked before every `LoadSession` call — this is not a multi-harness accommodation, it's correct ACP client behavior the codebase has always been able to skip.** `LoadSession` is a first-class, spec-documented ACP capability (`acp-go-sdk@v0.13.5/types_gen.go:44-46`, linking to `agentclientprotocol.com/protocol/session-setup#loading-sessions`; "Defaults to false if unset"), not a Goose extension — the current code calls `conn.LoadSession` unconditionally (`run.go:810` in the pre-unification numbering) only because Goose has always advertised it, so the gap was latent and harmless. Since this project only ever supports genuine ACP agents, implementing the capability check correctly is simply "support whatever ACP defines" — no special-casing per harness. `establishSession` reads `AgentCapabilities.LoadSession` off the `Initialize` response before attempting `LoadSession`; if false, this is a hard error surfaced distinctly ("harness does not support resuming a session"), not a silent fresh-session fallback that would quietly lose history. Practically, this makes `AgentCapabilities.LoadSession = true` a real admission requirement for any harness catalog row meant for multi-turn chat (nearly a given for a capable coding agent, but state it as a fact to verify when adding a harness, not an assumption).
4. **A second write site, and the field to compare against.** Add `goose_sessions.harness_instance` (relation → `harness_instances`, not required), populated at both write sites — `saveGooseSession` (`api/agent.go:389-402`, called from inside `establishSession` now, not `initSession`) and `schedule_importer.go:96-102`. `delete_session.go:54` resolves its `Target` from this field. `delete_session.go:62`'s `UnstableDeleteSession` and the *identical* call inside orphan-compensation (`run.go:800` in the pre-unification numbering) are both Goose-private unstable methods — a non-Goose harness that doesn't implement either should log and proceed with the local `goose_sessions` row deletion regardless; both call sites need this handling, not just one (round 3 found only `delete_session.go` had been addressed).

The `chats`-update hook from the first revision is kept as a fast-fail UX nicety only (reject an obvious `chats.harness` edit immediately with a clear error, instead of waiting for the next prompt) — `establishSession`'s check is the actual guarantee and does not depend on the hook catching anything. Per the existing hook-registration precedent (`hooks/timestamps.go:50-54` binds `OnRecordCreate("chats")`/`OnRecordUpdate("chats")`), it must use those **non-`Request`** variants — `*Request` hooks are skipped by backend `app.Save` calls, including the `agent` role's own writes, which matters for §5.8. `core.Record.Original()` gives the pre-update value for comparison.

**A stated consequence, not previously called out:** for a `supports_live_config = false` harness, `launch_key` (§4.3) is the resolved `harness_models.id`, so switching that chat's model changes which `harness_instances` row it resolves to — which `establishSession`'s pin check then rejects exactly like a harness change, forcing "start a new chat" on a mere model switch for such a harness. Defensible (the alternative is silently stranding history), but a real, user-visible behavioral rule worth stating rather than discovering.

#### 5.6.1 Harness is not derived from model alone

Resolving harness only via `harness_model_override → harness_models.harness` (the original draft's only path) makes a harness with zero `harness_models` rows unselectable, and puts "pick a model" ahead of "pick a harness" — backwards relative to §1's terminal analogy (pick the binary, then configure it). `chats.harness` (§4.1) fixes this: it is the primary signal; `harness_models.harness` is only consulted as a fallback when `chats.harness` is unset but a model override is. The `chats` fast-fail hook checks `chat.harness_model_override`'s harness against `chat.harness` when both are set — but per the TOCTOU/poco-fallback discussion above, this is a nicety, not the guarantee; the check inside `establishSession` (§5.6) is what actually prevents a `poco_configs.harness_model` reassignment (a path this hook cannot see, since it never touches `chats`) from producing a mismatched dial.

### 5.7 Interaction with `poco_configs.workspace_folders`

`workspace_override` overrides **only element 0 (cwd)**; `AdditionalDirectories` is always the union of the poco's `workspace_folders[1:]` regardless of whether `workspace_override` is set. This matches the terminal mental model from §1 — "I `cd`'d somewhere else, my existing tooling directories still apply" — and avoids a user's cwd choice silently dropping a poco's configured additional directories.

### 5.8 Path validation on `workspace_override` — checked in the right namespace, at both write and use

Moving cwd from `poco_configs` (superuser-only: `createRule`/`updateRule: null`) onto `chats` (writable by the chat's owning user, and by the `agent` role per its existing update rule) is a real privilege change, not a neutral relocation: it lets an authenticated user, or the agent process itself, set the next session's cwd to an arbitrary path — including wherever the harness's own provider-key file lives (`/goose/config/keys.env` inside the *goose* container specifically, per `docker-compose.yml`/`hooks/goose_config.go:42,96`).

**A write-time hook alone is not sufficient, for two reasons:** (1) `filepath.Clean` + symlink resolution run in *PocketBase's own mount namespace*, which is not the harness's — PocketBase does not have `/goose/config` mounted the way the goose container does, so a local stat/symlink-resolve can't see what the harness will actually resolve the path to; and (2) even a value that's legitimate at write time (a real subdirectory of `/workspace`) could be swapped for a symlink escaping the workspace root *after* validation, by anything with write access inside `/workspace` itself — which includes the harness's own shell-execution tool calls, gated separately by `tool_permissions`, not by this check.

Given (1), validation cannot rely on resolving symlinks locally at all — it must be a **textual, prefix-based check**: after `filepath.Clean`, the value must equal the workspace root (`GOOSE_WORKSPACE`, default `/workspace`) or have it as a path-segment prefix (`/workspace/...`), with no `..` segments surviving the clean. This check runs identically in two places: the `chats` write hook (fast-fail UX, using the non-`Request` hook variants per §5.6) **and** again inside `establishSession` (§5.6) immediately before the resolved value is used as `Cwd`, since the write-time check cannot itself be sole enforcement (a `poco_configs.workspace_folders` value takes the same path with no `chats` hook covering it at all, and the symlink-swap scenario in (2) is real regardless of hook timing).

Given (2), a symlink created inside `/workspace` *by the harness's own tool access* after validation passed is an accepted residual risk, not a hole this feature introduces: the harness already has that capability today via its existing shell/file tool calls, gated by `tool_permissions`, and this design does not change that gate. What this validation is actually for is narrower and load-bearing on its own: stopping a `workspace_override` *value itself* from ever pointing outside `/workspace` in the first place, regardless of who wrote it.

### 5.9 Constrained combinations

`harness_models` already constrains which models are valid for which harness (unique on `(harness, model)`) — the client only offers models that have a row there for the selected harness. A model additionally requires the current user to have a `provider_keys` row for that model's `provider`; `models.provider` and `provider_keys.provider` are both plain, uncanonicalized text (no shared enum), so the client-visible filter in this design makes a casing/naming mismatch (`Anthropic` vs `anthropic`) user-visible as "my model list is empty" for the first time — worth normalizing on write in a future pass, noted here rather than solved (§7 open items).

## 6. Coordinator changes (the actual surgery, spelled out)

The original draft's "`Coordinator.Config.GooseURL` becomes a per-chat resolved value" undersold this as a one-line change; it's a signature change, a new shared function (§5.6's `establishSession`), and a couple of fields that need to ride on `SessionProfile` because the coordinator package is deliberately PocketBase-agnostic (`profile.go`'s doc comments; no `core.App` anywhere in it) and has no other way to see harness-catalog booleans or do its own DB lookups.

### 6.1 `SessionProfile` carries `Target` and the two capability flags

`SessionProfile` (`profile.go:32-37`) gains `Target struct{ URL, Secret string }`, `SupportsLiveConfig`, and `SupportsGooseExtensions bool`, all populated by `buildSessionProfile`'s resolution (§5.1) — this is the concrete answer to "where do these live" for both §5.6's pin check and §6.4's `selectApplier` fix, neither of which the coordinator can resolve on its own. `DialFunc`'s signature (`run.go:53`) becomes `func(context.Context, acpsdk.Client, Target) (acp.Conn, error)`; an empty `Target` falls back to today's `Config.GooseURL`/`GooseSecret`. Per §5.4/§5.4.1, `Target` needs no transport field and no per-transport branching in `Dial` — every harness is dialed the same way, through the existing `internal/agent/acp/websocket.go` `Dial`/`wsStream` unchanged, because every `harness_instances.acp_endpoint` is a websocket URL (Goose's native one, or a bundled adapter's).

### 6.2 Dial sites: two collapse into `establishSession`, two stay separate

`runLoop` and the replay path (renamed per §5.6) both call the new shared `establishSession`, which resolves `Target`, performs the pin check, dials, and runs `Initialize`/`session/new`|`load` — one implementation instead of two independently-maintained ones. `delete_session.go:54` and `AdminConn` (`admin.go:77`) remain separate, deliberately: `delete_session.go` resolves its `Target` from `goose_sessions.harness_instance` (§5.6) since deleting a session on the wrong harness is a real failure once more than one exists, while `AdminConn` takes no `Target` at all and always dials the default/compose-managed Goose unconditionally — the concrete meaning of §5.5's "stays Goose-only in v1" at this call site.

### 6.3 Workspace fallback

`c.config.Workspace` is the cwd fallback (currently `run.go:556-559` and `run.go:780-783`, both folding into `establishSession`). This design mandates every catalog harness mount its workspace at the same path (`/workspace`) as Goose does, so the existing single fallback constant remains correct; a harness needing a different mount path is out of scope for v1.

### 6.4 `selectApplier` must actually branch, and must account for session *mode* too

`selectApplier` unconditionally returning `PerSessionApplier` (§2) is fine with one harness and a live bug with two: a harness with `SupportsGooseExtensions = false` (now available on `SessionProfile`, §6.1 — not something `selectApplier` has to infer from the ACP `InitializeResponse` alone, which can't express a Goose-private capability) will reject the `_goose/unstable/session/system-prompt/set` call at `profile.go:130`, `Apply` returns an error, and that error propagates out of `establishSession`, killing the entire run. `selectApplier` must consult `SessionProfile.SupportsLiveConfig`/`SupportsGooseExtensions` and skip the system-prompt call for `SupportsGooseExtensions = false` harnesses, applying only standard `session/set_config_option` calls gated by `SupportsLiveConfig`.

That alone is not the whole fix. `PerSessionApplier.Apply` starts by delegating to `GlobalConfigApplier.Apply` (`profile.go:104`), which issues `SetSessionMode` whenever `p.Mode != ""` (`profile.go:76-82`) — and `buildSessionProfile` sets `p.Mode = "approve"` on every path (`api/profile.go:64,90`), unconditionally, regardless of harness. `"approve"` is a Goose-specific mode id (`poco_configs.mode` ∈ `auto|approve|smart_approve|chat`); a non-Goose harness advertises its own, different mode set, and an unrecognized mode id sent via `session/set_config_option` fails the same way the extensions call does — the exact class of bug this section exists to prevent, just via a path the extensions-only framing above doesn't cover.

The authoritative mode list is only known once it arrives in the `session/new`/`session/load` response (`res.Modes`) — which is necessarily after the call that produces it, so gating cannot happen at `selectApplier`'s call site (before either request). Fix: `Apply`'s signature gains the session's advertised modes, threaded from `res.Modes` inside `establishSession` (both the `NewSession` and `LoadSession` branches) into the existing post-create `applier.Apply` call; `Apply` skips `SetSessionMode` (logging, not erroring) when `p.Mode` isn't among the advertised modes — guard `modes == nil` (the field is `omitempty`) as "don't skip, don't assert," not as an empty set, so a harness that simply omits the field on `session/load` doesn't silently lose its mode entirely.

## 7. Client-facing surface

`ChatDao.save`/`createChat` gains optional `harness`, `harnessModel`, and `workspaceOverride` parameters, threaded from a new chat-creation step in `chat_list_cubit.dart`/`chat_list_screen.dart` that lets the user pick cwd + harness + model before the chat is created (today it's a bare title-only insert). This is the actual point where "the user chooses, like terminal Claude Code" becomes real — everything upstream in this spec exists to make that choice mean something.

## 8. Testing

- **`buildSessionProfile` fix (§2)**: a chat with `harness_model_override`/`workspace_override`/`harness` set but **no** `poco_config` and **no** `is_default` poco (the fresh-deployment state) must still resolve those chat-level fields — this is the regression test for the early-return bug, and it should fail against today's code before the fix lands.
- **`establishSession` is one implementation, exercised by both callers (§5.6)**: a single test suite against `establishSession` covers both `runLoop` and the renamed replay path — not duplicated per-caller — since that's the entire point of unifying them.
- **Harness pinning, checked at use (§5.6)**: a chat whose resolved harness differs from `goose_sessions.harness_instance` must be rejected inside `establishSession`, before any dial, with a clear error — including via a path the `chats` hook cannot see (e.g. reassigning the *poco's* `harness_model` to a different harness, with `chats` itself never written). The `chats` hook's own fast-fail case (a direct `chats.harness` edit) is a separate, additional test, not a substitute for the use-time one. Also test the creation-race shape directly: two concurrent `establishSession` calls minting a new session for the same chat — assert the loser's `saveGooseSession` fails on `UNIQUE(chat)` and its stranded remote session is orphan-compensated away, not that the pre-dial check alone prevented the race.
- **One connection per chat's session (§5.6, item 2)**: a live run reserved for a chat, plus a concurrent replay-path call for the same chat, must result in exactly one dialed connection — assert the replay path serves the hub's existing snapshot/buffer and never dials.
- **`AgentCapabilities.LoadSession` gating (§5.6, item 3)**: a harness whose `Initialize` response omits/`false`s `LoadSession` must fail clearly on any resume attempt for that chat, never silently start a fresh session in its place.
- **`selectApplier` branching (§6.4)**: against a harness with `supports_goose_extensions = false`, assert no `_goose/unstable/...` call is issued and the run does not fail; against `supports_live_config = false`, assert no `session/set_config_option` call is issued either; against a harness whose advertised `res.Modes` doesn't include `"approve"`, assert `SetSessionMode` is skipped (logged) rather than sent and erroring.
- **stdio adapter framing (§5.4.1)**: a message near/above the stdio-side default `bufio.Scanner` limit (64 KiB) round-trips intact through the adapter — this is the regression test for the "two limits, not one" finding; a message exercising the full raised limit (up to the matching 64 MiB ceiling) also round-trips intact on both the stdio and WS legs.
- **Instance resolution**: fake docker-socket-proxy client — first-time chat→harness selection provisions exactly one instance (reused for a second chat on a `supports_live_config = true` harness; a second distinct instance, keyed on `launch_key`, for a `supports_live_config = false` harness with a different model). Include a case for `IMAGES=0`-style pull failure surfacing into `harness_instances.last_error` rather than a silently stuck row.
- **Volume/network resolution (§5.1.2)**: a fake `GET /containers/pocketcoder-pocketbase/json` response drives the cached volume/network names used in a subsequent create call — assert the wrong-name-silently-creates-empty-volume failure mode is what this test is guarding against (i.e. assert the *resolved* name is used, not a guessed one).
- **Event watcher (§5.3)**: fake Docker event stream — a `die` event flips the matching row to `stopped`, a healthy `start` flips it to `running`; a startup reconciliation sweep corrects a row left `running` from a container that died while PocketBase was down; both the sweep and any stop/remove skip `managed = false` rows.
- **Path validation (§5.8)**: `workspace_override` entries outside the workspace root (via `..` traversal or a non-prefix-matching absolute path) are rejected both by the `chats` hook and independently by `buildSessionProfile`/`initSession`'s own check — test each enforcement point separately, since neither is a substitute for the other (a `poco_configs.workspace_folders` value only ever reaches the second one).
- **Client**: existing chat-creation tests extended to cover the new optional params defaulting to today's behavior when omitted (backward-compatible bare-title creation still works).

## 9. Open questions / risks carried forward

- **Resource footprint, reweighted.** Each non-Goose harness instance is another always-on daemon, and per §5.1.1 its image must already be pulled onto a possibly modest VPS — disk, not just RAM, is now a binding constraint, and it interacts directly with `docs/superpowers/specs/2026-07-29-linode-boot-time-image-provisioning-design.md`. No lazy-stop-when-idle mechanism is designed here (the `created`/`updated` fields on `harness_instances` exist partly to make that easy to add later); the first real non-Goose harness should validate whether this matters in practice before building one. Separately, §5.4's spawn-per-connection adapter puts a fresh process cold-start on the critical path of *every* prompt for a stdio-native harness (not just first use) — worth measuring against the underlying binary's actual startup time before assuming it's negligible.
- **Network egress for non-Goose harnesses.** `NETWORKS=0` (§5.1.2) means only one network can be attached at container-create time, so a provisioned harness joins `pocketcoder-agent` and nothing else — worth confirming that's sufficient for it to reach its provider's API (it is a plain bridge network with normal outbound NAT, so this is expected to be fine, but state it rather than leave it implicit, since `pocketcoder-goose-egress` exists as a separate, more restricted network for exactly this purpose on the Goose side and a non-Goose harness doesn't get it).
- **Provider string normalization** (§5.9): `models.provider`/`provider_keys.provider` casing/naming consistency is not enforced anywhere today; this design makes a mismatch user-visible for the first time via client-side filtering. Worth a normalize-on-write hook in a follow-up, not solved here.
- **Migration mechanics — simplified by having no existing deployments.** An earlier revision treated §4 as needing to be additive-only, worried about `1756000000_schema.go`'s one-shot `ImportCollectionsByMarshaledJSON` migration never re-running against an already-provisioned box. That risk doesn't apply here: there are no deployments running this schema yet, so `schema.json`/the migration/seed files are edited directly, including the new indexes in §4. If a future revision needs to support re-homing a chat to a different harness (this spec deliberately doesn't), that's the point where `goose_sessions`' own unique indexes would need to change, and by then real deployments may exist — it should get its own design pass with the additive-only discipline this revision was able to skip.
- **Per-chat worktree convenience**: still explicitly deferred (§3). If stomping between chats sharing a `workspace_override` value becomes a real complaint, a future PocketBase-side "create me a worktree" action is the natural next step, not automatic isolation.
